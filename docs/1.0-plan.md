# The 1.0 plan, and how to work through it

This is the execution plan for Folio 1.0 and the **briefing file every subagent reads
first**. It exists because the work is twenty issues across six ordered phases, the
ordering is a set of real constraints rather than a preference, and this repository's
invariants are dense and mostly silent when broken.

Read this, then `CLAUDE.md`'s "Invariants that are easy to break by accident". Neither
replaces the other: that section is what breaks, this file is what to build and in what
order.

The tracker is the source of truth for *what* each item is. Every issue carries the
evidence, the rejected alternative, and a dated decision comment. **Read the issue and
its comments before starting it** — the decision is in the comment, not the body, for
the twelve that were decided on 2026-09-07.

- Issues: `gh issue list --repo brendanmckenzie/folio --milestone "Phase 2 · Admin"`

## Why the order is what it is

Four hard constraints. Everything else is grouped to keep two agents out of one file.

1. **#5 first.** It is the only thing that can verify #4: `scripts/space-test.mjs`
   already carries 26 checks against the peer list and presence, and the runner
   currently throws its exit code away. Fix the gate, run all 22 scripts, and record
   which were green — every later phase is verified against that baseline.
2. **#13 before the tag.** Un-exporting is free now and a major bump the moment `1.0.0`
   exists. It is the only item whose cost changes at the tag.
3. **#14 before #7.** The role audit wants a screen rendered as a `viewer` asserting a
   control is absent, which is exactly the harness #14 builds.
4. **#2 last in phase 2.** #3, #4 and #2 all edit `Prototype.tsx`, and a mechanical
   rename makes every other diff in that file unreadable.

## Orchestration rules

From the September 2026 six-spec run (48 commits, ~30 subagents) and the August spec 24
run. These are not style preferences; each one cost something to learn.

- **Scope every agent by file, never by task.** Give it an explicit "your files, and only
  these" list, plus any concurrent agent's list, and tell it: a failure in their files is
  not yours, report rather than fix. Two tasks that sound unrelated share files more
  often than expected.
- **Sequential agents in one tree remain right.** Phase 1 is the only place two can run
  at once, and only because their file sets are provably disjoint.
- **Never run `pnpm test` while an agent is live.** The workerd pool starves: the symptom
  is `Timeout starting cloudflare-pool runner` and a 5-second test reporting 346s, which
  reads exactly like a regression. Use `npx vitest run --project unit <file>` or
  `--project workers <file>` while agents are running.
- **Ban file-level `cp` backups.** For a break-it check, revert in place. A `cp` backup
  of a shared file once got restored over another agent's edits.
- **The highest-value instruction is "verify by breaking it."** Ask every agent to
  disable the invariant its work turns on and report which tests go red. This repeatedly
  caught things a green suite could not: a rate limiter that still limited but silently
  reset every hour; a `dryRun` that spent money while every "nothing written" assertion
  stayed green. **If an agent does not report that check, run it yourself before
  committing** — it is the assertion most likely to be absent.
- **Verify the gates yourself. Never commit on an agent's report.** Commit per issue, so
  a bad one is one revert.
- **A stall tells you nothing.** Six on that run: most had finished and died before
  reporting, one produced nothing, one stopped mid-file. On a stall, `git status` for the
  file list, then the gates by exit code. Recovery is cheap; trusting the notification is
  not.
- **An independent reviewer after each risky item.** Opus, reading the diff against the
  issue's decision comment and its rejected alternative — explicitly told the gates are
  already green so it spends its budget on faithfulness rather than re-implementing. On
  the spec 24 run this found the only real bug, which every gate had passed.

### Gate discipline

`CLAUDE.md` has the full list. The two that bite hardest:

- **`biome ci` prints `Lint: No issues found` even when its format check failed further
  up.** Run `./node_modules/.bin/biome ci .` — the direct binary — and read the exit
  code. `pnpm exec biome ci .` can be rewritten by a shell hook into something that
  prints a plausible summary and never runs biome; it has reported no issues over four
  real errors.
- **`cmd | tail; echo $?` is `tail`'s status, which is always 0.** Never gate on a piped
  command's output.

### Two things phase 3 measured that later phases own

- **`release.mjs`'s `exports resolve` check cannot see a named export.** It is
  `existsSync` on each subpath's leaf *file* target (`scripts/release.mjs:139`), so
  it would pass a barrel that had dropped every name inside it. That was harmless
  while the surface was only ever added to and is not any more, now that #13 has
  removed 37 names — and it is the only gate that exercises the package the way a
  consumer does. **#1 owns `release.mjs`; close it there.** The check that actually
  covered #13 was ad-hoc: parse both consumers' `import` statements, then resolve
  every name against the built ESM and the emitted `.d.ts`.

  103 came from `README.md`, `AGENTS.md`, `UPGRADING.md`, `docs/**` and both

### What the reviews caught, and what that says about the method

The plan's "independent reviewer after each risky item" earned its place on #4.
Every gate was green — including the e2e script and a new 27-test unit file — and
an opus reviewer reading the diff against the decision comment found two defects
that all of it passed:

- **The `space` flag was answered per *route*.** It rode the shell's HTML
  bootstrap, filled from `bindings`, which only `routes/editor.ts` passed. Fine
  while the channel was the editor's alone; the mount made it every screen's flag,
  so a browser entering at `{base}` or `{base}/content` read `undefined` and — since
  `useSpace` memoises its store on `enabled` — stayed off for the whole session.
  The feature was absent on the ordinary entry path. It is on `GET {base}/api/me`
  now, which is where `routes/shell.ts`'s own comment had said it belongs.
- **`reload: true` was a no-op on the edit screen**, the one screen the notices are
  addressed to, because only Content and Documents register a reload.

Both now have assertions that go red when the fix is removed. The general lesson,
recorded in `pages.tsx`: **a bootstrap field is answered per route and cached by
the client for the session, so a route that forgets one is a feature that stays
off.**

Two habits that paid, beyond the plan's own rules:

- **Correct a comment that a change makes false, in the same commit.** Four of the
  six issues left at least one behind — #4's `PrototypeBoot.space` still said
  "nothing reads it yet", #14's three files still said the admin suite mounts
  nothing. An agent scoped by file correctly reports rather than edits these, so
  they are the orchestrator's to close.
- **Ask what the *proof* proves.** #3's issue supplied a grep whose two names were
  one discriminator and one false positive; #4's agent-written test asserted a seam
  the runtime never reached; two of `preview-share`'s passing checks were vacuous.
  In all three the assertion existed and did not mean what it looked like.

### What phase 2's second review caught, and the three rules that came out of it

#7 got the same treatment as #4 and it paid the same way: nine findings, **two of
them real defects that all five green gates had passed**, and both in work the
orchestrator had done by hand rather than delegated.

- **A vacuous assertion, again, and by the same mechanism.** The asset panel's
  admin case asked the *whole document* for `Describe` and `Delete`, with a comment
  claiming they could only be the panel's "because the grid's needs a selection and
  nothing is ticked". False: `AssetBrowser` renders the bulk bar whenever `bulk` is
  true regardless of the row count, and its buttons are merely `disabled`, which
  `queryAllByRole` finds perfectly well. Both names were present before the panel
  rendered anything — so the admin half stayed green with the panel's entire write
  register removed. Scoping it to the panel's landmark makes that break red.
- **`Unfiled` used as a fallback where it is a claim.** `folders.find(…) ??
  'Unfiled'` states that a file in *Brand* is unfiled for the length of a round
  trip, and permanently if the fetch fails, because the failure lands in
  `folders.error` and a fallback never looks there.

Three rules, each of which cost something here:

- **A render test cannot see a loading state, so logic that has one belongs in a
  pure function.** The first break-it check on the `Unfiled` bug *passed* with the
  naive spelling, because `mountAt` flushes four times before it asserts. The
  loading and deleted-folder cases are only observable outside a mount, which is
  why `folderNameFor` is in `assets-model.ts` with a four-case unit test. A mount
  proves the resolved case and nothing else.
- **Absence of an affordance is not absence of a handler.** #7's first cut withdrew
  the asset drop target by not spreading its handlers, which hands the drop back to
  the browser — whose default action for a file dropped on a page is to *navigate to
  it*. A viewer's stray drop replaced the admin with a JPEG and discarded whatever
  was open, which is worse than the 403 toast it removed. `useDropTarget` takes an
  `enabled` flag and swallows the event instead.
- **A build that emits the wrong artifact and exits 0 is not a gate.** `main.tsx`
  has always said a dynamic import of the admin ships it unstyled and called it "a
  failure only `pnpm build` catches". Measured while doing #2: `pnpm build:demo`
  **exits 0**, drops `folio-admin.css` entirely and writes
  `assets/Admin-DUuKy0oE.css` instead. Nothing was watching but a person reading
  `ls`. `test/unit/admin/admin-entry.test.ts` now asserts it as source text.

Two things worth knowing before scoping an admin issue, both of which made a
plan file list wrong:

- **A screen's controls are often not in the screen's file.** #7's list said "the 7
  list screens" and the real surface included `AssetBrowser.tsx` (2,000 lines, 49
  controls), `AssetDetail.tsx`, `AssetPicker.tsx` and `content-model.ts`. Five of
  the seven screens were not even receiving `me`.
- **An issue's own evidence can be stale in a way that inverts the fix.** #8's
  issue described 11px grey headings under 13px crumbs; `ListHeader` had since
  grown a `level` prop, so eight screens were already `h1` at 15px and the
  duplication was *worse* than described, not better. `Schedules` was the one screen
  that had never been fixed and was still the original defect verbatim.

## The phases

Sizes are this repository's own convention, from `PARITY.md`: **XS** under an hour,
**S** about a day, **M** a few days. Relative weight, not a quote.

`fork` below means `subagent_type: "fork"`, which inherits the orchestrating session's
full context. Use it wherever the work depends on invariants the session has already
loaded and a fresh agent would have to rediscover. Everything else is a fresh
`general-purpose` agent with the issue as its spec.

## Definition of done, per issue

Every one of these before the commit, in this order:

1. The issue's stated proof, from its `**Proof:**` line on the gate sheet or its decision
   comment.
2. The break-it check, run by you if the agent did not report it.
3. `pnpm typecheck` — exit code.
4. `./node_modules/.bin/biome ci .` — the direct binary, exit code.
5. `pnpm test` — exit code, and only with no agent running.
6. Commit, subject stating what is now true, body naming the alternative it beat. Read
   `git log` first; there are no `feat:`/`fix:` prefixes and no trailing period.
7. `gh issue close <n> --comment "…"` naming the commit.

`pnpm build` before a phase boundary rather than every commit, except for #2 and #3 where
a broken static import in `src/admin/main.tsx` ships the admin unstyled and only `pnpm build`
catches it.
